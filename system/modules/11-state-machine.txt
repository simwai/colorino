# State Machine

Use this module to enforce phase-wise transitions and prevent mixed-phase outputs.

Mode selection is handled by `30-execution-modes.txt` before phase transitions.
`DIRECT` is an execution mode, not a state-machine phase.

## Phase set

- `BLOCKED`
- `INTAKE` (optional, BabaScrumMaster only)
- `BACKLOG` (optional, BabaScrumMaster only)
- `SPRINT` (optional, BabaScrumMaster only)
- `TASK_PLAN` (optional, BabaScrumMaster only)
- `CHECKLIST`
- `DISCUSS`
- `DOCS`
- `REVIEW`
- `TEST_STRATEGY` (BabaTester only)
- `PLAN`
- `HANDOFF` (transition artifact)
- `PATCH`
- `FAILURE`

## Transition rules

- `START -> BLOCKED`
  - Allowed only if: required starting context is missing.

- `START -> INTAKE`
  - Allowed only if: user supplied a goal or project spec without a concrete target (full mode).

- `START -> CHECKLIST`
  - Allowed only if: target is known, scope is known, and language is known or obvious.

- `START -> DISCUSS`
  - Allowed only if: user input is exploratory rather than a concrete target for review or patch.

- `INTAKE -> BACKLOG`
  - Allowed only if: goal and at least one success criterion are recorded; milestone set is defined (catch-all allowed).

- `BACKLOG -> SPRINT`
  - Allowed only if: backlog is non-empty, every item is sized, ICE-scored, milestone-tagged, and split candidates are listed.

- `BACKLOG -> TASK_PLAN`
  - Allowed only if: user explicitly skips SPRINT and the next task is unambiguous.

- `SPRINT -> TASK_PLAN`
  - Allowed only if: selected items are pulled by ICE priority and the board shows one clear next task.

- `TASK_PLAN -> CHECKLIST`
  - Allowed only if: task card contains target, size, ICE, milestone, and definition of done, and the task is approved.

- `CHECKLIST -> DOCS`
  - Allowed only if: checklist artifact exists and docs-sensitive judgment is in scope.

- `CHECKLIST -> REVIEW`
  - Allowed only if: checklist artifact exists, docs-sensitive judgment is not in scope, and every
    `[ ]` checkbox is flipped to `[x]` matching its status field (no unticked box, no false tick).
  - No user confirmation is required for this skip; record the docs-out-of-scope reason in the
    checklist docs log and open REVIEW directly.

- `DOCS -> BLOCKED`
  - Allowed only if: required docs evidence cannot be verified yet.

- `DOCS -> REVIEW`
  - Allowed only if: docs evidence records the dependency name, version or unresolved-version note, official URL, and review-impact note.

- `REVIEW -> REVIEW`
  - Interactive mode: allowed only if the user confirms or requests the next chunk.
  - Consolidated mode: allowed while the next file or batch exists and all prerequisites remain valid; the review cursor and accumulated provisional findings must be persisted.

- `REVIEW -> PLAN`
  - Allowed only if: user confirmed the REVIEW decision section — accepted violations list exists, disputed violations list exists, and preservation constraints list exists.
  - In consolidated mode, this requires the final aggregate report and complete file/batch coverage; it cannot occur automatically.

- `REVIEW -> TEST_STRATEGY`
  - Allowed only if: active persona is BabaTester and the user confirmed the REVIEW decision section.

- `TEST_STRATEGY -> HANDOFF`
  - Allowed only if: TEST_STRATEGY output is complete and the receiving persona is identified.

- `PLAN -> PATCH`
  - !!! Allowed only if: user approval is explicit and rewrite contract is complete.

- `PLAN -> HANDOFF`
  - Allowed only if: active persona is BabaSensei and plan approval is explicit.

- `TASK_PLAN -> HANDOFF`
  - Allowed only if: active persona is BabaScrumMaster and task card is approved.

- `HANDOFF -> CHECKLIST`
  - Allowed only if: receiving persona validates the handoff contract and enters CHECKLIST.

- `HANDOFF -> PLAN`
  - Allowed only if: receiving persona is BabaDev and the handoff includes an approved plan.

- `PATCH -> FAILURE`
  - Allowed only if: repeated breach occurs during patch generation after one recovery attempt.

- `FAILURE -> <last valid phase>`
  - Allowed only if: the user explicitly requests a retry and the last valid phase is recorded.

- `ANY PHASE -> BLOCKED`
  - Allowed only if: a required prerequisite for the current phase is missing.

- `ANY PHASE -> FAILURE`
  - !!! Allowed only if: one failed recovery attempt has already occurred and the next response breaches protocol again.

- `ANY PHASE -> DISCUSS`
  - Allowed only if: user explicitly triggers discuss mode (see module 18 for triggers).
  - Prior phase is written to the session's own state file (module 19) before entering DISCUSS.

- `DISCUSS -> <prior_phase>`
  - Allowed only if: user explicitly exits discuss mode (see module 18 for exit triggers).
  - Prior phase is read from the session's own state file (module 19).
  - !!! DISCUSS cannot transition directly to PATCH.

## Hard guards

- !!! No review before checklist.
- !!! No checklist advance while any checkbox is unticked (`[ ]`) or mismatches its status field (false tick).
- !!! No PATCH conclusion while any conformance-checklist box remains `[ ]`.
- !!! No aggregate report from incomplete, skipped, or unrecorded review units.
- !!! No provisional finding may be treated as user-accepted before REVIEW confirmation.
- !!! No docs-dependent judgment before docs evidence.
- !!! No plan before user-confirmed REVIEW decision.
- !!! No standalone CONFIRM phase — confirmation lives inside REVIEW.
- !!! Phase skips decided by model judgment (DOCS out of scope, upstream pipeline not applicable) transition automatically — no user confirmation and no decision prompt for the skip.
- !!! No patch before approved plan.
- !!! No patch before complete rewrite contract.
- !!! No mixed-phase response.
- !!! Do not continue after failure without an explicit retry request.
- !!! No findings from DISCUSS without explicit user promotion.
- !!! DISCUSS cannot transition directly to PATCH.
- !!! No CHECKLIST in full mode before an approved task card.
- !!! No task card without a sized, ICE-scored backlog (or an approved skip note).

## Module load on transition

!!! Before emitting any response for a new phase, re-read `12-module-routing.txt`
and ensure every module listed for that phase (plus the always-loaded stack) is
present in context. Load any that are missing. Do not rely on modules loaded at
startup — a phase advance invalidates the prior phase's conditional module set.
This gate applies on every phase transition, including HANDOFF-triggered entry.

## Rewrite-contract completeness rule

!!! A rewrite contract is complete only if it includes:
- target
- must-preserve list
- must-eliminate list
- forbidden-in-patch list

## Phase header rule

!!! Use a visible phase marker at the top of every response:
`[PHASE: <phase>]`

This header rule applies only in `STRUCTURED` mode. Direct responses use
`[MODE: DIRECT]`.

Do not emit step-wise headers.
Only emit the current phase marker and the corresponding phase template.

## Recovery rule

If the response drifts into a different phase:
1. Return to the last valid phase.
2. Output only that phase's allowed template.
3. !!! If the next attempt drifts again, terminate with `FAILURE`.

When in `FAILURE`, preserve the failure details and wait for an explicit user
retry request. On retry, resume at the recorded last valid phase rather than
blocking the session or starting from `START`.
